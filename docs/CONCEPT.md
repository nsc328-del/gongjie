# 共界：共享世界角色扮演概念基线

状态：`v0.2 / 结构基线`  
主线：`main`  
文档所有者：主线维护者

## 1. 产品核心

共界不是多个角色聊天窗口的集合，而是一个由多名角色共同生活、各自只掌握部分信息的持续世界。

用户与任一角色发生的事情，只要被确认为事实，就可能改变世界时间、地点、角色关系、角色知识与其他角色之后的行为。共享的是同一个世界事实，不是同一个全知上下文。

体验必须同时成立：

- 角色是自主的人，不是同一助手换皮，也不是无条件满足机器。
- 私聊具有隐私；一个角色不知道的事不能因为模型拿到了数据库就突然知道。
- 已发生的事会留下后果，高潮或冲突不会自动把场景清零。
- 分支允许尝试不同走向，但只有被选为正史的路径能改变共享世界。
- 多角色同场最终应由同一场景编排驱动，而不是把几个单聊回复拼起来。

## 2. 真相的层级

系统中的内容分为四层，顺序不可颠倒：

1. **叙事文本**：角色或用户说了什么、描述了什么。
2. **状态提案**：裁判从文本中提取的事件、现场与关系变化，仍可能有误。
3. **分支事实**：通过领域校验后写入某条分支的事实，只对该分支成立。
4. **世界正史**：用户提升分支后，由该分支可见消息产生的事实进入共享时间线。

核心规则是“意图不是事实”。计划、威胁、幻想、猜测和未完成动作不能直接成为事件。UI 不得绕过领域规则直接写入正史；模型也没有最终裁决权。

## 3. 世界、场景与分支

### 世界

世界保存共享名称、前提、氛围、规则、当前正史时间、地点、角色和正史事件。

### 对话

当前阶段，每名角色在一个世界中拥有一条私人对话。对话负责消息历史，不直接代表世界真相。

### 分支

分支从一条可见消息处分叉，并继承该时点的场景快照，而不是父分支的最新状态。分支内的新事件默认不是正史。提升为正史时，只提升目标分支实际可见消息关联的事件；被截断的未来不能混入。

以下状态必须随分支分叉：

- 场景地点、时间、张力、未结线索、身体状态与情绪状态；
- 用户与角色的关系数值和关系痕迹；
- 欲望阶段、余波与该场景的临时约束。

当前实现只完成了场景快照。关系仍是全局写入，这是已知结构缺口，不是产品规则；由 `codex/world-core` 与 `codex/character-minds` 在接口稳定后共同收口。

## 4. 事实与认知

事件有客观事实和角色认知两个维度：

- `public`：成为正史后，世界中的角色可被视为能够获知，但上下文仍应按相关性选择。
- `private`：只授予参与者、目击者或后来被告知者。
- `secret`：必须显式记录知情来源，不因同场或同世界自动扩散。
- `misunderstood`：角色持有一个与客观事实不同的信念；错误信念不能覆盖事实本身。

知识是有来源的状态，不是把事件复制到提示词。未来的听闻、推断、怀疑和遗忘都应落在认知层，而不是改写世界事实。

## 5. 角色心智

一个角色至少由以下部分组成：

- 稳定身份：年龄、身份、人格、语言风格、标志行为；
- 欲望指纹：控制、依恋、嫉妒、风险、温柔等相对倾向；
- 关系状态：对用户及其他角色的信任、欲望、张力、标签和痕迹；
- 当前认知：亲历、听闻、相信、误解的内容；
- 动态阶段：克制、试探、推进、失控、余波等随场景变化的状态。

欲望阶段不是固定五段模板，导演可以根据角色指纹和局势选择路径，但每次变化必须由可追溯的互动触发。角色可以拒绝、争夺、嫉妒和改变策略。所有可创建角色必须明确为成年人。

## 6. 上下文编译

上下文编译器负责回答一个问题：此刻这个角色为了自然地继续行动，应该看到什么？

输入包含世界、目标角色、目标分支、场景、可见消息、关系和角色知识。输出是模型无关的请求上下文。编译器必须：

- 只注入角色有权知道的事实；
- 区分事实、信念与误解；
- 保留未解决的动作、关系余波和场景连续性；
- 根据相关性组织长上下文，而不是因为模型支持 1M 就无条件倾倒全部记录；
- 不承担网络请求、数据库写入或世界裁决。

长上下文能力降低了压缩频率，但不取消上下文编译。选择信息的目的首先是维持角色认知边界和叙事焦点，其次才是节省 token。

## 7. 导演与多人场景

导演负责节奏与状态提案，不负责宣布真相。当前裁判只提取一轮后的事件、场景和关系变化；后续导演应加入欲望阶段和余波，但不加入随机事件生成器。

多人场景必须拥有独立的场景实体，明确：

- 在场者、当前说话者、可打断窗口；
- 公开动作、私密动作和各自目击范围；
- 每名角色的独立动机与下一步意图；
- 同一轮中谁行动、谁观察、谁误解；
- 场景结束后哪些结果进入各自私聊记忆。

同场角色不能由一个模型回复中的多个名字冒充。即使一次请求生成多人的文本，领域层也必须保留每名角色的独立状态与认知。

## 8. 模型运行边界

模型运行层只处理：协议适配、请求发送、流式事件归一化、累计快照、取消、用量和错误分类。它不理解世界、角色、NSFW、正史或剧情节奏。

API Key 只保存在本地密钥文件或环境变量中，不进入 SQLite、接口返回值和 Git。上层只依赖模型无关的 `RequestContext` 与 `ReplySnapshot`。

## 9. 界面原则

界面要让世界状态可感知，而不是像数据库管理器：

- 世界、角色、地点和时间线有清晰空间层级；
- 私聊与多人同场是两种明确模式；
- 分支、正史和当前所处路径必须一眼可辨；
- 角色知道什么、误解什么可以被查看，但不以开发者术语解释；
- 创作入口服务于快速塑造世界与角色，不向用户暴露内部表结构。

面向用户的页面不放“本模块用于……”之类解释文案。若功能需要说明才能理解，优先重做信息层级和交互。

## 10. 模块与依赖方向

依赖方向固定为：

`web → api → scenes → cognition → domain/storage`

`scenes/cognition → ai`，`ops → storage/ai`

禁止反向依赖：存储不导入提示词，模型适配器不导入场景，前端不直接操作数据库。

| 分支 | 责任 | 主要目录 | 不负责 |
| --- | --- | --- | --- |
| `codex/world-core` | 世界事实、分支、正史、快照、迁移 | `gongjie/storage/`，未来 `gongjie/domain/` | 提示词与 UI |
| `codex/character-minds` | 角色、关系、欲望阶段、知识与误解 | 未来 `gongjie/cognition/minds.py` 等 | 模型协议 |
| `codex/context-compiler` | 角色可见内容选择与请求上下文 | `gongjie/cognition/compiler.py` | 事实写入 |
| `codex/model-runtime` | Provider、流式、错误、用量与取消 | `gongjie/ai/` | 剧情判断 |
| `codex/director` | 节奏、余波、状态提案与裁判 | `gongjie/scenes/adjudication.py`，未来导演模块 | 最终真相 |
| `codex/multichar-scenes` | 多人在场、轮次、打断与目击范围 | `gongjie/scenes/` 的多人模块 | 单纯拼接私聊 |
| `codex/creator-ui` | 游玩界面、时间线、检查器与创作器 | `static/`，必要的 `gongjie/api/` 契约 | 领域规则捷径 |
| `codex/local-ops` | 密钥、备份、导入导出、诊断 | `gongjie/ops/` | 角色与剧情语义 |

跨模块契约应先在本文件写清，再落代码。分支合并顺序优先遵循：世界核心 → 角色心智 → 上下文 → 导演 → 多人场景 → 界面；模型运行与本地运维可在契约稳定后独立推进。

## 11. 当前可依赖的闭环

结构基线已具备：世界与角色编辑、角色私聊、流式回复、独立状态裁判、公开/私有事件、角色误解、场景快照、历史分叉、正史提升、OpenAI-compatible 与 Anthropic Messages 适配、本地密钥保存。

当前闭环不代表最终设计。下一阶段优先解决世界核心与角色心智的分支一致性，再扩展欲望阶段、余波和真正的多人同场。
