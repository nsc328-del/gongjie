# 生成链路精简与验收

状态：本地实现与回归已完成；真实模型结算验收未通过，本轮未部署。

日期：2026-09-12。范围：Web 的状态提案协议、目的地回复与有限修复。存储格式仍为 17，不改变角色的认知权限、三层真相、原子提交或访问空间隔离。

## 已确认的过度设计

### 反复核对和跨层返工

此前相同测试中的普通地点转告、预约、补一句记住名称，分别使用 6、11、6 次模型调用，耗时 61.72、123.67、63.88 秒。各类核对占总耗时约 87%–89%；预约的两次正文生成合计只有 5.54 秒。

预约的第一篇正文已经通过地理核对，但状态提案把“稍后”写成了另一时刻。内层提案修复失败被外层当作正文错误，于是重写角色答复，再核对整段正文。第二篇又引入新条件并漏填关系证据。字段提取问题因此改变剧情内容，而且增加等待。

现在正文校对与提案修复各自有界。正文通过后固定其内容和地理结论；只修复提案，失败不会重新抽取角色答复。已有地点的用途、指代和玩家授权统一在待发布正文中核对，不再单独重证其地理设定；真正新增地点仍保留独立准入核对。

### 模型重复维护相同状态

旧协议让模型在变化对象之外，另维护以字符串字段路径连接的 evidence 表；主模板不含完整证据结构，后面又追加多段说明。实测中，模型去掉关系数值变化后仍改变关系说明，却再次漏掉所需证据。

现在模型只使用一份格式：事件和关系的 evidence 放在各自对象内部；时间与承诺使用带 value 和来源的对象。场景层转换成领域层的既有格式，领域校验、语义核对和存储不改用另一套事实规则。旧模型输入格式明确拒绝，不保留双协议。

地点变化已经由已核对的场景方案和抵达结论得出，模型不再重复填写玩家与人物地点。事件时间继承本轮有效时钟，也不再单独重填。实际改变世界时间仍必须提供原文依据。

### 同一请求重复携带正文

此前正文核对同时发送完整 reply 和包含同一正文的 reply_sources，提案输入也重复包含原文与逐句来源表。单条请求保留一份完整、有序、标明说话人的来源即可；不同请求所必需的当前状态、历史与认知边界继续保留。

### 重复快照和不完整反馈

原有归一化只删除重复的时间、地点和部分玩家状态；现在也移除相同的现场状态、关系零增量、相同关系说明和逐项相同的承诺列表。完整空增量直接完成，不为已经确认的状态再发一次审核；真正改变的自由文本仍接受核对。

审核同时返回 approved=true 和非空 issues 时不再接受。字段类型与必需字段严格校验；修复获得全部问题，不被原先的四条上限截断。历史回执保留原来的展示上限。

## 没有删除的约束

- 逐人可见信息与实际在场；同场耳语、纸条和心声不能直接给所有人。
- 来源编号、逐字引用、世界归属、玩家承诺的说话方和关系增量上限。
- 独立语义核对；active_threads、关系说明等字段也可能夹带错误事实，不能只因字段被称为软状态就跳过。
- 正文、提案、事实分离；失败不能被标为成功，磁盘故障保留可恢复任务，语义拒绝有明确终点。
- 整组原子写回与幂等恢复。它们直接解决已经发生过的半写入与重复结算问题。

当前没有必要为此再引入通用工作流引擎或独立 MCP 服务。调用次数的主要成本在模型核对，包装成更多服务不会消除重复判断。存储模块较大是后续维护问题，本次没有为追求文件拆分而改变其事务边界。

## 验证结果

全量 Python 回归和现有前端 Node 回归通过，diff 检查通过。关键覆盖包括新格式仍拒绝伪造来源与旁观者秘密引用、只改关系说明也必须有证据、来源可追溯到正确说话人、提案修复不触发正文重写，以及新旧地点不同审核路径的原子提交。

正常已有地点的目的地回合为“规划、正文、正文核对、提案、证据核对”五次调用；新建地点多一次设定准入。这个调用数来自确定性管线回归，不是模型速度承诺。真实对照使用独立新世界和相同输入，不改动线上玩家的剧情。第一批结果如下，失败记录未删除，也未重采样覆盖。

### 审核器实验：未采用

冻结真实失败请求，逐项制作修正来源和承诺的正确对照，再加入同场递纸的观察边界对照。共 8 份，每种配置仅运行一次，不改原文或现有剧情。

- 精简提示、关闭 thinking：每条 1.67–3.37 秒，4/8 符合预期，但正确对照全部被拒绝，不能采用。
- 同一精简提示、保留 low thinking：每条 33.09–46.84 秒，2/8 符合预期，5 条耗尽额度没有判决，另有一条错误提案被通过，不能采用。

这些实验没有替换应用中的审核器，也没有进入线上。缩短提示词或关闭思考本身不构成可靠优化。

### 提取约束增强后的独立对照

单独强化“引用对应行为人”“所有文本保留转述归属”“不擅自接受对方的约定条件”，其余审核器保持原版本。相同第 1 条输入总计 83.94 秒；正文 4.91 秒完成，审核占 87.76%。提案格式正确，但修复后的审核再次把 8192 token 全用于 reasoning，留下真实 pending；按预定规则停止，没有发送后两条输入。

### 输出预算实验与最终状态

最后重放同一条失败审核请求一次，system/messages 完全冻结，仅将 max_tokens 从 8192 调为 16384。34.56 秒取得完整拒绝判决，实际输出 7024 token，其中 reasoning 6830。因为本次实际未超过原上限，结果不能证明抬高预算稳定解决问题，可能包含模型输出波动；该配置也没有进入应用。原提案仍有普通追问长期化及证据说话方不匹配，不应为结束等待而接受。

最终本地回归：Python 114 项通过，现有 Node 前端回归通过，diff 检查通过。覆盖创建世界、普通流式回复、目的地缓冲、结算拒绝与恢复、同场知情隔离、检查点存读及无变化去重；没有做浏览器视觉验收，本轮未改前端。

本轮没有执行生产部署，也没有提交 Git。线上服务保持 active；所有真实实验使用独立目录和数据库，原失败状态完整保留。部署脚本仅作准备，未执行。

## 后续设计判断

应保留的复杂性是角色限知、公开与秘密、可追溯来源和原子事务。值得进一步收敛的是同一信息在事件、active_threads、关系说明等多个可写字段中重复表达；它扩大了模型必须保持一致的范围，审核又可能把描述和事实混淆。下一阶段宜先明确哪些字段是真实可写状态、哪些只是从已确认来源派生的展示，再减少重复提取与审核。这个产品语义调整本轮没有静默实施，也没有增加 MCP 服务或通用工作流。
